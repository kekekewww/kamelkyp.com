# WP3 Footer: Studio footer settings and a CMS-driven public footer

Status: implementation spec, 2026-10-13. Work package `wp3-footer`.
Branch: `claude/wp3-footer` (its own worktree, cut from `origin/main` 6bd682a; integration plan
`docs/superpowers/plans/2026-10-13-finish-code-work.md` §1, whose §2 and §9 win over this spec).
Companion docs, which win where they are more specific: `docs/content-schema.md`, `docs/admin-architecture.md`,
`docs/content-architecture.md`, brief `docs/superpowers/specs/2026-09-24-content-studio-brief.md`.

---

## 1. Goal

1. Replace the stub at `/studio/settings/footer` with a working **KAMEL STUDIO → Settings → Footer** screen. The owner
   can, without code: reorder every footer group, show or hide groups, edit bilingual group labels, create and delete
   custom link groups, and add, edit, reorder, show/hide and remove links (bilingual labels, one address) inside
   custom groups.
2. Make the public footer read only CMS data for everything that is content: group order, visibility and labels
   come from `link_groups` / `link_group_labels`; custom links from `links`; "Find Me" from `social_links`; "Contact"
   from `brand.contactEmail`; "Navigate" follows `site.navigation`; "Services" uses `site.serviceAreas` names. Code
   keeps only site structure (route paths) and UI-copy defaults. The legacy module
   `app/lib/content/footer-repository.server.ts` (and its dead hard-coded GitHub default) is removed.
3. Keep the Kamel-only brand (brand guard on every saved label and address), keep the footer price-free, keep
   sample content out, and keep every existing public footer assertion green (6 groups with the e2e fixture).

Out of scope: the `/admin/*` → `/studio` flip (integration package), footer lead/copyright/location text (already
in Settings → Site / Brand), the brand contact address decision (content-architecture §8 item 5), visual redesign of
the public footer.

## 4. Design

### 4.1 Decision: where footer data lives

**Tables, not a settings row.** content-schema §6.2 (R6) keeps footer link groups in `link_groups` / `links` /
`link_group_labels` and names Studio → Settings → Footer as their editor; the `settings` table only accepts
`key IN ('brand','site')` (`migrations/0005_cms_schema.sql`, `settings` CHECK), so a footer document would need a
table rebuild, which is not additive. The footer keeps its own tables and adds no column.

What becomes CMS data, and what stays code (R7 keeps site structure in code):

| Part | Source after WP3 |
| --- | --- |
| Group order, visibility, label (all groups) | `link_groups.sort_order`, `.enabled`, `link_group_labels` |
| Links of custom groups (`work_resources`, legacy `footer` etc., Studio-created) | `links` (per-locale rows) |
| Navigate links | `site.navigation.items` (order + visible); labels = header UI copy; paths = `NAV_PATHS` |
| Services links | `site.serviceAreas[].name` (UI-copy default when empty) → area paths; plus "Start a project" (UI copy `cta`) → `/commission` |
| Find Me links | `social_links` where `enabled = 1` |
| Contact link | `brand.contactEmail` |
| Legal links | Terms → `/terms`, Privacy → `/privacy` (UI copy) |
| Default group labels (when a stored label is empty) and the D1-unavailable fallback | `FOOTER_SYSTEM_GROUPS` constants (UI copy) |

### 4.2 Group model

Five **built-in** (system) groups, one row each in `link_groups` (seeded by migration 0010, §7), plus any number of
**custom** groups. The legacy `social` key is ignored everywhere (it became `social_links`).

| key (`stable_key`) | Seed id | Default label zh / en | Position when no row | Hideable | Deletable | Links |
| --- | --- | --- | --- | --- | --- | --- |
| `navigate` | `seed-footer-navigate` | 導覽 / Navigate | lead | yes | no | derived |
| `services` | `seed-footer-services` | 服務 / Services | lead | yes | no | derived |
| `find_me` | `seed-footer-find-me` | 社群 / Find Me | trail | yes | no | derived (`social_links`) |
| `contact` | `seed-footer-contact` | 聯絡 / Contact | trail | yes | no | derived (`brand.contactEmail`) |
| `legal` | `seed-footer-legal` | 條款與網站 / Legal | trail | **no** (always shown) | no | derived |
| anything else (`work_resources`, `footer`, `workRepository`, `otherWebsite`, `postReference`, `custom-<uuid>`) | row id | stored only | stored position | yes | yes | `links` rows |

Rationale for "Legal always shown": Terms and Privacy must stay reachable from every page (the commission flow
collects personal data under those documents); hiding them is not a content choice. The Studio shows "Always shown"
instead of a switch and the server refuses `toggle-group` for `legal`; the public composer ignores a stray
`enabled = 0` on `legal`.

**Logical link** (Studio view of `links`): `{ key, label: {zh, en}, url, enabled }`, stored as one `zh` row and one
`en` row with the same `sort_order`, the same `url` and the same `enabled` (R11: URL and flags are shared). The loader
pairs rows by `(group_id, sort_order)`; leftovers (legacy one-locale rows, two rows in one locale at one position)
become their own logical links with a load note. Saving always writes complete pairs.

### 4.4 Public composition rules (`composeFooterGroups`)

Input (all already localized for one locale):

```ts
export type FooterGroupRecord = {
  id: string;            // link_groups.id
  key: string;           // stable_key
  sortOrder: number;
  enabled: boolean;
  label: string;         // stored label for this locale ("" when none)
  links: Array<{ id: string; label: string; url: string }>; // enabled rows for this locale, in order
};
export type FooterSources = {
  locale: Locale;
  groups: readonly FooterGroupRecord[];
  navigation: ReadonlyArray<{ key: NavKey; visible: boolean }>;
  serviceAreas: ReadonlyArray<{ key: ServiceAreaKey; name: LocalizedText }>;
  socialLinks: ReadonlyArray<{ id: string; label: string; url: string }>; // enabled, localized, safe
  contactEmail: string;
};
export function composeFooterGroups(sources: FooterSources): FooterGroup[];
```

1. **Order.** Drop records with key `social`. Sort stored records by `(sortOrder, id)`. A built-in key with no record
   gets a virtual record: missing `navigate`/`services` go first (canonical order), missing
   `find_me`/`contact`/`legal` go last (canonical order). With no rows at all (fallback) the order is navigate,
   services, find_me, contact, legal.
2. **Visibility.** Skip records with `enabled = false`, except `legal`. Skip any group whose final link list is empty.
3. **Label.** Built-in: `label.trim()` or the default label for the locale. Custom: `label.trim()`; when empty the
   group is skipped in that locale (content-schema §1.2 rule 3; no cross-locale fallback, never a raw `stable_key`).
4. **Links by kind** (ids keep today's values so React keys and tests stay stable):
   - `navigate`: visible `navigation` items in order → `{ id: NAV_LINK_IDS[key], label: getSiteCopy(locale)[key],
     url: localePath(locale, NAV_PATHS[key]) }` with `NAV_LINK_IDS = { work: "works", services: "services-overview",
     about: "about", writing: "writing" }` (today's ids, `footer-repository.server.ts:42-62`).
   - `services`: for each key of `SERVICE_AREA_KEYS` in canonical order (mixing, song_transition, software): label =
     localized `serviceAreas[key].name` trimmed, else the default (混音/Mixing, 歌曲銜接/Song Transition,
     軟體與互動/Software & Interactive); url `/mixing`, `/song-transition`, `/services/software`; ids `mixing`,
     `transition`, `software`. Then `{ id: "commission", label: copy.cta, url: localePath(locale, "/commission") }`.
   - `find_me`: `socialLinks` as given.
   - `contact`: when `contactEmail.trim()` is non-empty, one link `{ id: "email", label: email, url: "mailto:" + email }`.
   - `legal`: `{ id: "terms", 服務條款 / Terms, /terms }`, `{ id: "privacy", 隱私說明 / Privacy, /privacy }`.
   - custom: stored links with non-empty label and `isSafeFooterUrl(url)`; `url` passes through `footerHref`.
     Defence in depth for rows not written by the Studio (legacy `/admin/links` until WP5, raw SQL): a custom group
     label or link label matching `SAMPLE_MARKER` (§4.8) is treated as empty, so the group or link is omitted.
     (The brand guard stays server-only and is not applied here: its deny list must never reach a client bundle,
     `brand-guard.server.ts:1-6`.)
5. **URLs.** `isSafeFooterUrl` (moved from `site.server.ts:51-58`, hardened): `/…` but not `//…`, and no `\`,
   whitespace or control character anywhere (browsers treat `/\host` as `//host`), or an `https:` / `mailto:` URL.
   The hardening rejects nothing that the seeds, the fixtures or the legacy admin (`https:`/`mailto:` only) write.
   `footerHref(locale, url)`: `/zh`, `/en`, `/zh/…`, `/en/…` unchanged (legacy rows); any other `/…`
   becomes `localizeHref(locale, url)` (`app/lib/cms/public/build-views.ts:47-50`); absolute URLs unchanged.
   `app/lib/cms/public/footer.ts` contains no `/studio` string (Studio source links live in `footer-model.ts`), so
   `studio-access.spec.ts:52-57` ("the public site does not link to the Studio") keeps passing.
6. **Group ids.** Built-in groups use their key (`navigate`, `services`, `find_me`, `contact`, `legal`); custom groups
   use the row id (as today, e.g. `seed-work-resources`).

Result on the seeded databases (loopback e2e, worker tests): Navigate, Services, Work & Resources, Find Me (only with
an enabled social link), Contact, Legal: the same order, labels and links as today.

Public read statement (replaces `site.server.ts:300-310`; the batch stays at 4 statements):

```sql
SELECT g.id AS group_id, g.stable_key, g.sort_order, g.enabled AS group_enabled,
       gl.label AS group_label, l.id AS link_id, l.label AS link_label, l.url AS link_url
FROM link_groups g
LEFT JOIN link_group_labels gl ON gl.group_id = g.id AND gl.locale = ?1
LEFT JOIN links l ON l.group_id = g.id AND g.enabled = 1 AND l.locale = ?1 AND l.enabled = 1
WHERE g.stable_key <> 'social'
ORDER BY g.sort_order, g.id, l.sort_order, l.id
```

`getPublicSiteContext` folds the rows into `FooterGroupRecord[]` (one record per `group_id`, links where `link_id` is
not null) and calls `composeFooterGroups` with `site.value.navigation.items`, `site.value.serviceAreas`, the
already-filtered `socialLinks` and `brand.value.contactEmail`. Only the composed `FooterGroup[]` enters the public
loader data: labels of hidden groups and hidden links never reach the served HTML. `fallbackSiteContext` calls it with `groups: []` and
the default settings (result: navigate, services, legal; unchanged from today).

Per group row (`<li>` in `<ol aria-label="Footer groups">`):

- `normalizeFooterUrl`: trim; bare email (`/^[^\s@/:]+@[^\s@/:]+\.[^\s@/:]+$/`) → `mailto:<value>`; bare host

  locale segment (stored paths are locale-less, like `CtaHrefSchema`, `app/lib/cms/schemas/brand-settings.ts:19-32`);
  anything else trimmed.
- `footerUrlProblem` (after normalization): empty → "Enter an address."; `/…` valid unless it starts with `//`,
  contains `\` or whitespace, or its first path segment is a `RESERVED_PATH_PREFIXES` entry (`/studio`, `/api`,

  `studio-access.spec.ts:52-57`); `mailto:` valid when the path contains `@`; `https:` valid without user/password

  address or a site path such as /works."; over 2048 → "This address is too long."

Loader batch (one `db.batch`): (1) `SELECT id, stable_key, sort_order, enabled FROM link_groups WHERE stable_key <>
'social' ORDER BY sort_order, id`; (2) labels of those groups; (3) `links` of those groups `ORDER BY group_id,
sort_order, locale, id`; (4) `settingsStatement(db)` (`app/lib/cms/settings.server.ts:25`); (5) `SELECT id,
label_i18n, url FROM social_links WHERE enabled = 1 ORDER BY sort_order, id` (filtered by `isSafeFooterUrl`).

Fingerprint: SHA-256 (`crypto.subtle`, available in Workers and Node) of
`JSON.stringify({ label: [zh, en], links: rows sorted by (sortOrder, locale, label, url) → [locale, label, url,
sortOrder, enabled] })`, where `label` is the **stored** label rows (`""` for a missing locale or a missing row, never
the UI default) and the rows are the group's `links` rows (each row's own `sort_order`/`enabled`). The group's
`enabled` and `sort_order` are not part of it, so toggle and reorder do not change it and an open editor survives
them. The read-then-batch check has a small race window; it is acceptable for a single-owner Studio (the same
trade-off as the social screen, which has no check at all).

`footer-model.ts` `localizeRecords(groups, sources, locale)` builds the preview's `FooterSources` exactly as
`getPublicSiteContext` does: stored labels per locale, enabled link pairs whose label in that locale is non-empty,
and social links filtered per locale by non-empty label and `isSafeFooterUrl` (`site.server.ts:335-343`). Worker
test 6.2 #13 asserts parity with the public composition.

Id resolution for every intent: an existing non-`social` row id is accepted; a built-in seed id
(`seed-footer-<key>`) is accepted only when **no row has that built-in `stable_key`** (the loader shows such groups
with `stored: false`), and `ensureFooterSystemGroupStatements` recreates the row at the start of the same batch;
anything else is 404. (If a row with the key exists under another id, the loader lists that id, so the seed id is
never sent; accepting it would make the `UPDATE` a silent no-op because the ensure insert is ignored on the
`stable_key` UNIQUE constraint.)

Messages: every non-default message in this table (the 409 and 422 texts) is returned with
`actionError(code, { status, message })` (`responses.ts:45-65`; pass `status: 409` explicitly, the default is 422).
Throwing `CmsError("stale_revision")` would answer with the generic "This entry changed elsewhere."
(`errors.ts:41-56`). 404s may throw `CmsError("not_found")`. Every result echoes `intent` (the convention
wp6-hygiene §4.1.4 makes general).

React Router revalidates the loader after every fetcher action, so the list, the preview and the fingerprints refresh.

## 7. Migration needs

One new migration: **`migrations/0010_cms_footer_groups.sql`**. `0009` is claimed by wp2-pricing-terms
(`0009_pricing_terms_studio.sql`, `2026-10-13-wp2-pricing-terms.md` §7); WP1, WP4, WP5 and WP6 add none. The two
files touch disjoint tables, so they work in either landing order: `wrangler d1 migrations apply` applies every
unapplied file by name (a gap while only one has landed is fine, and a `0009` landing after `0010` is still applied),
and the worker tests apply all files in name order. The numbers are fixed by the integration plan (§2.1): nobody
renumbers, so the `applyMigrationQueries` prefix `"0010"` in §6.2 stays exact. Additive (no schema change, no
`UPDATE`, no `DELETE`) and idempotent (`INSERT OR IGNORE` on the `stable_key` UNIQUE constraint and the
`link_group_labels` primary key); it reads nothing besides `link_groups`.

```sql
-- 0010_cms_footer_groups.sql — footer group placement becomes CMS data
-- (docs/superpowers/specs/2026-10-13-wp3-footer.md §7, content-schema "Footer link groups").
-- Additive and idempotent: INSERT OR IGNORE only; nothing is updated or deleted
-- and a second run changes nothing. The five built-in footer groups get
-- link_groups rows (position, visibility, label); their links stay derived at
-- read time (site navigation, service areas, social links, brand contact email,
-- legal pages). Custom groups keep their rows in `links`. Positions wrap the
-- existing groups so the public footer order is unchanged.

INSERT OR IGNORE INTO link_groups (id, stable_key, sort_order, enabled)
SELECT 'seed-footer-navigate', 'navigate',
  COALESCE((SELECT MIN(sort_order) FROM link_groups
            WHERE stable_key NOT IN ('navigate', 'services', 'find_me', 'contact', 'legal', 'social')), 30) - 20,
  1;

INSERT OR IGNORE INTO link_groups (id, stable_key, sort_order, enabled)
SELECT 'seed-footer-services', 'services',
  COALESCE((SELECT MIN(sort_order) FROM link_groups
            WHERE stable_key NOT IN ('navigate', 'services', 'find_me', 'contact', 'legal', 'social')), 30) - 10,
  1;

INSERT OR IGNORE INTO link_groups (id, stable_key, sort_order, enabled)
SELECT 'seed-footer-find-me', 'find_me',
  COALESCE((SELECT MAX(sort_order) FROM link_groups
            WHERE stable_key NOT IN ('navigate', 'services', 'find_me', 'contact', 'legal', 'social')), 30) + 10,
  1;

INSERT OR IGNORE INTO link_groups (id, stable_key, sort_order, enabled)
SELECT 'seed-footer-contact', 'contact',
  COALESCE((SELECT MAX(sort_order) FROM link_groups
            WHERE stable_key NOT IN ('navigate', 'services', 'find_me', 'contact', 'legal', 'social')), 30) + 20,
  1;

INSERT OR IGNORE INTO link_groups (id, stable_key, sort_order, enabled)
SELECT 'seed-footer-legal', 'legal',
  COALESCE((SELECT MAX(sort_order) FROM link_groups
```
